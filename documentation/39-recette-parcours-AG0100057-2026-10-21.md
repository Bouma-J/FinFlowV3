### Première tentative

`idProduitRemb = "COMPTE-COURANT"`, valeur alors enregistrée dans le mécanisme : **HTTP 200 / `responseCode = 409`**.

```text
For input string: "COMPTE-COURANT" !
```

### Reprise demandée par l'utilisateur

La correspondance du mécanisme est modifiée par l'API d'administration en `DEGRESSIVE`. La revue et l'autorisation sont renouvelées, puis l'envoi est repris sur le même dossier, avec le même identifiant externe et la même clé d'idempotence : **HTTP 200 / `responseCode = 409`**.

```text
For input string: "DEGRESSIVE" !
```

FinFlow renvoie HTTP 400 dans les deux cas. Le journal `034b72d1-b6c4-4075-8e98-12538429afeb` contient deux tentatives, le dernier message envoyé et le motif de refus. Les deux réponses brutes sont conservées dans les preuves de cette recette.

Les appels réels sont espacés d'au moins trois secondes au sein des séquences, TLS reste vérifié et les secrets d'authentification sont masqués. Aucun troisième code de remboursement n'a été essayé au hasard.

**Conclusion sur le champ :** ces réponses indiquent que le CBS essaie de convertir la valeur reçue en nombre. Elles ne fournissent pas l'identifiant numérique correct du mécanisme et ne permettent pas de le déduire du mot DEGRESSIVE. Cet identifiant ou son catalogue source est nécessaire pour terminer la recette positive. Le rejet ne prouve pas que tous les autres champs seraient acceptés.

## Correction apportée à l'identifiant externe

Pour les nouveaux dossiers transmis réellement, `externalId` utilise maintenant l'UUID du dossier. La référence métier séquentielle est conservée dans FinFlow. Cela évite la collision entre références identiques de différentes installations ou filiales, observée sur CR-2026-00002.

Lorsqu'une tentative existe déjà, le générateur reprend son `externalId` conservé dans le journal. Il ne change donc pas silencieusement l'identifiant d'un dossier déjà envoyé. Deux nouveaux tests couvrent cette stabilité et cette compatibilité. Le précédent dossier AG0100053 n'a pas été retransmis.

Le script de recette accepte maintenant un scénario distinct pour les données client, les conditions de crédit et l'analyse. Il bloque aussi un rejeu automatique lorsqu'une transmission a déjà été tentée ; la seconde tentative de cette campagne a fait l'objet d'une reprise explicite demandée par l'utilisateur.
